# 代码 review 系统化模板

按以下顺序审查代码，每一类都给出具体证据（行号 / 片段），不要只说"可能有"。

## 审查维度

### 1. 🔴 正确性（Correctness）
- 并发安全：是否有共享变量未加锁？goroutine 是否会泄漏？
- 资源泄漏：文件 / 网络连接 / 锁是否 defer 释放？
- 边界条件：空 slice / nil map / 空字符串 / 0 值时行为？
- 错误处理：忽略的 error、错误传播链、defer 内 error 覆盖？
- panic 风险：nil 指针 / 除零 / 类型断言失败 / index out of range？

### 2. 🟡 安全性（Security）
- 凭据泄漏：token / password / API key 是否硬编码或日志打印？
- 路径穿越：用户输入的路径是否做 `filepath.Clean` + 范围限制？
- 命令注入：拼接用户输入到 shell 命令时是否用参数化？
- 权限提升：sudo / chmod 777 / setuid 是否合理？
- 信任边界：从外部（HTTP / 文件 / 用户输入）来的数据是否校验？

### 3. 🟡 性能（Performance）
- 时间复杂度：O(n²) 是否有更好的算法？
- 空间复杂度：大对象是否 leak？
- I/O 热点：是否有不必要的磁盘 / 网络读写？
- 锁粒度：是否过度锁 / 锁竞争？
- goroutine 数量：是否无界创建？

### 4. 🟢 可读性（Readability）
- 命名：变量名是否自解释？
- 函数长度：单函数 > 80 行能否拆？
- 注释：复杂逻辑是否解释"为什么"而非"做了什么"？
- 错误信息：错误信息是否对调试友好（含上下文）？

### 5. 🟢 可维护性（Maintainability）
- 重复代码：3 处以上相似逻辑能否抽象？
- 魔法数字：硬编码常量是否提取为命名常量？
- 抽象层次：函数是否做了多层抽象不一致的事？
- 测试覆盖：核心逻辑是否有单测？

## 输出格式

按维度分组，每条问题必须包含：
- **位置**：文件:行号 或 函数名
- **严重度**：🔴 / 🟡 / 🟢
- **问题**：1-2 句话描述
- **建议**：具体的修复方案（代码片段更好）

最后给一个总评：✅ 可以 merge / ⚠️ 需要小改 / ❌ 需要重写。

## 重要

- **不要为了凑数编造问题** —— 没问题的代码直接说"这块写得好"。
- **不要重复用户已经知道的事**（如"这个函数叫 foo"）。
- **要给优先级**：3 个 🔴 > 10 个 🟢，先列严重问题。
